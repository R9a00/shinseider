# 調査・材料・作成・完成稿点検

## 目的

公式要項と経験者の知見を参照し、本人の材料と根拠をそろえ、実際の提出フォーマットへ内容を配置し、完成稿を根拠と要件に照らして点検できる。受賞確率や通過を保証しない。

## 正本と実装

- `data/application_support.yaml`: 公式6項目ごとの追加質問、調査資料、4段階のAI指示、品質点検基準。
- `application_context.py`: MCPのデータ検査・文書抽出・引継ぎ・指示文生成。
- `site/static/application-core.js`: ブラウザーでの同じデータ形式・引継ぎ・指示文生成。
- `site/templates/application.html`: 材料編集、調査の反映、フォーマット・完成稿読込み、AIへ渡す一式の出力、品質点検結果の保存。

## データの契約

`shinseider.application-context/1`。公式6項目ごとに使える本文・根拠・不足と次の質問・図表候補を分離。根拠はURL/資料名/確認日/情報種別/本人による申告か外部で確認した情報かを記録する。本人の実績を記事から補完しない。

旧5テーマと深掘りは参照材料として取り込む。6項目の本文へ無断で確定変換しない。文脈データはブラウザー保存・JSON出力・MCPで同じ形式を使い、別AI・別会話へ引き継げる。

フォーマットと完成稿はPPTX/PDF/DOCX/TXT/MDからテキストを抽出する。ページ・スライド順を保持する。画像のみ・抽出不能・暗号化は明示し、レイアウト/図/写真の確認をテキスト抽出で済ませない。読込みはローカルで行う。原本をAIへ渡して視覚的に確認する手順を付ける。

品質チェックは本文の引用、根拠、重大度、直し方、未確認範囲を返す。完成稿・フォーマット・材料が変われば以前の結果を最新扱いしない。空欄がないこと・ファイルが存在することを完成判定にしない。

## 受入条件

1. 公式/経験談/提案を区別し、根拠と日付を読める。
2. 6項目の不足から追加質問・調査を始め、本文と宿題を分離して保存できる。
3. 既存データを保持して文脈JSONの出力・再読込・MCP保存が往復一致する。
4. フォーマットと完成稿の抽出結果、原本と文脈を使う作成/点検指示を出力できる。
5. 変更前の点検結果を現行稿の合格と誤表示しない。
6. 保存失敗・不正JSON・対応外形式・読めないページで無断にデータを失わない。

自動LLM APIや自動提出は行わず、利用者のAIに指示文と原本を渡す既存方式を拡張する。MCPの検索指示は接続先AIの検索能力を使い、サーバーが検索済みと偽らない。

## 実装上の範囲

- 文脈JSONは最大200万文字。ファイルは各15MB、PDF/PPTXは100ページまで、抽出文字は50万文字まで。DOCX/TXT/MDは1単位の本文として読み、ページ境界は未確認とする。
- PDF.js / fflateを版固定で同梱。MCPはpypdfと標準XML/ZIPを使う。ブラウザーとPythonの同じ入力に対するbinding・生成指示の一致を検査する。
- 本文と図の意味、主張の根拠、実証の質は接続先AIと本人が点検する。機械チェックは空欄・ページ数・抽出警告に限る。ファイルの存在を意味的な完成判定にしない。
- MCPの原本読込みは登録済みworkspace内のmaterialsに限定する。ブラウザーでは選択した原本のみ読む。外部へ原本を自動送信しない。
- 旧控え/旧骨子/フカボリへの影響：既存IDを変えず、追加文脈を控えに含める。以前の控えにapplicationが無い場合は現在の文脈を保持する。
