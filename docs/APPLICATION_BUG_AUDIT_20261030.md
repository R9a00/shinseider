# 作成・点検機能のバグ点検（2026-10-30）

## 対象と方法

EXP PS選択のattg内の公開正本 `shinseider-next/shinseider-poc` をGitで再観測し、main f3f451bから別worktreeで点検。元の未コミット変更と本番確認記録を保全した。新しいapplication画面・保存・文書抽出・MCPを重点とし、既存13ページの回帰も検査した。

点検前の通常検査はNode 12件/Python 11件が通っていた。入力の変更タイミング、別タブ、容量不足、旧スクリプトのキャッシュ、古い文脈を使った保存を加え、通常ケースでは出ない不具合を再現して修正した。

## 確認した不具合と修正

| 項目 | 再現条件・影響 | 修正 |
|---|---|---|
| 保存失敗を成功表示 | ブラウザー保存が容量不足でも点検欄に「保存しました」と表示 | 保存結果の戻り値を確認し、未保存と控え保存を案内。古い保存の完了で新しい検査エラーの未保存状態を消さない |
| 6項目を別タブで編集できない | 別の項目でも材料配列全体が競合。初回利用時にも発生 | 固定6項目を欄単位で差分比較し、初期値を共通化 |
| 文脈の控えに他タブの更新が欠落 | 他タブの本文を保存後、古いタブで控えを出すと本文が含まれない | 共通snapshotを使用。未保存・入力途中の内容も残す |
| 指示文の対象と本文が不一致 | ハッシュ生成待ちに編集すると、IDは古い材料、本文は新しい材料になる | 開始時の複製から両方を生成 |
| 遅れた処理が新しい入力へ反映 | ファイル/JSON読込みや指示生成中に編集しても、後から古い処理が反映される | 入力版と内容を比較し、変化した場合は取り込み・出力を中止 |
| 古いMCP文脈が新しい点検を消す | 点検本文はbindingの対象外なので、以前の文脈を保存すると新しい点検を上書きできる | 点検本文を含むrevisionで比較。旧binding保存でも点検変更を拒否 |
| 文脈保存の競合・途中失敗に弱い | 比較と書込みが別処理で、JSONを直接切り詰めていた | ロック内で比較・保存。一時ファイルから原子的に置換。一般の記録ツールからの直接更新も拒否 |
| 原本ファイル名の制限 | 「提出 フォーマット (1).txt」がMCPで不正名として拒否される | 空白と括弧を許可。作業フォルダ外への参照禁止は維持 |
| 文書中の数字・段落が変わる | Wordのタブ・改行を無視して「4」「36」を「436」へ連結。入れ子段落も重複 | タブ・改行を保持し、入れ子段落を一度ずつ抽出 |
| ブラウザー/Pythonの境界値の差 | JSON長の空白・Unicodeの数え方と、ページ番号1.0の扱いが異なる | 文字数・整数の扱いを統一し、対応しない拡張項目・不正文字・本文が空の点検記録は明示拒否 |

## 検証

- Node 17件合格。非同期指示の固定、初回を含む別タブの独立編集/同一欄競合、控えの統合、不正データと文字数境界を含む。
- Python 23件合格。ブラウザーでの容量不足、遅延したファイル/JSON/指示、控え、壊れたPDFを読み込んだ際の元データ保持、Wordの改行、MCPの古い保存版拒否、競合保存、置換失敗時の原本保持を含む。
- MCPは実際のSTDIOサーバーと通信し、revisionとbindingの違い、再起動後の読戻し、旧入力の拒否を確認。
- 既存サイト回帰と13ページの375px/1280px検査に合格。横あふれ・JS例外なし。
- 新しいテストは `site/tests/test_application_bugs.py`、Nodeの共通保存/文脈テスト、既存STDIOテストへ追加。テスト内のデータは架空。実在ユーザーの保存データやMCP設定は操作していない。

実行記録： [再現ログ（Node）](application-bug-audit-20261030/reproduced-node.log)、[再現ログ（画面・MCP）](application-bug-audit-20261030/reproduced-browser-mcp.log)、[検証集計](application-bug-audit-20261030/verification.json)。再現ログは修正前の意図した失敗を含む。

## 範囲の限界

検査はmacOSとCIのLinux/Chromiumを対象とし、すべてのブラウザーやOS・任意の文書形式を網羅した保証ではない。AIの未知の誤りの検出率、実際の公式フォーマットへの最終適合は今回のバグ検査に含まれない。MCP利用者はサーバーの更新・再接続が必要。既存のexpected_bindingは限定互換を残し、新しいクライアントにはexpected_revisionを案内する。
